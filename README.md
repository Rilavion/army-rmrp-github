## 1. Фактическое состояние версии

Подготовка: **20 октября 2026 года**. Эта версия использует Node.js API и PostgreSQL. В браузере нет облачного ключа и соединения с Supabase или Firebase. Совместимый `api-client.js` позволяет сохранённым модулям работать через сервер с проверкой прав.

Внешняя основа — исходный ВС РФ; функциональные редакторы состава и тестов перенесены из ЦГБ. Новый журнал поставок переносит рабочие операции отдельного проекта ВС РФ в PostgreSQL портала. Медицинские услуги ЦГБ не включены в армейский сайт.

`learn.html`, `training.html` и `service-requests.html` открываются по прямым ссылкам, но отсутствуют в навигации. Публичность страницы не означает публичность персональных данных: состав, жалобы, премии, проверки и результаты экзаменов защищены сервером.

В подготовленной папке для GitHub нужны **все файлы**, включая скрытые `.gitignore`, `.gitattributes`, `.dockerignore` и `.env.example`. Количество файлов не определяет, что следует исключать. В пакет не входят `node_modules`, `.local`, `.env`, пароли, пользовательские фото и дампы БД. `HANDOFF-MANIFEST.json` содержит размеры и SHA-256 файлов экспорта.

- [Развёртывание, первый администратор и резервные копии](docs/DEPLOYMENT.md).
- [Вход по статику, одобрение регистрации и обязательное подключение техадминистраторами](docs/AUTHENTICATION.md) — вход только по статику, **приём регистраций выключен по умолчанию** (`REGISTRATION_ENABLED=false`); обязательны должность, звание, Discord и фото игрового УДО.
- [Необходимые Discord-вебхуки и назначение каждого](docs/WEBHOOKS.md).
- [Таблицы PostgreSQL, колонки и SQL](docs/DATABASE.md).

Исходники поставок перенесены из `patriki-vsrf-supply-control-upload`: `SupplyForm`, `HistoryView`, `StatsView`, фильтры, расчёты и экспорт. Вместо Firebase используется защищённый API PostgreSQL; оформление встроено в армейскую оболочку. Сборка воспроизводится командой `npm run build:frontend`; готовые файлы уже включены в репозиторий.

## 3. Схема работы

```text
Браузер → HTTPS / reverse proxy → Node.js API → PostgreSQL
                                  ↓
                         каталог загруженных фото

Изменение / отчёт → очередь outbox → worker → Discord webhook
```

Браузер обращается к API своего домена. PostgreSQL доступен только серверу. Сессия использует HttpOnly-cookie. Worker расшифровывает URL вебхука и отправляет сообщение; сбой Discord не отменяет сохранение данных сайта.

Preview использует временный PostgreSQL-совместимый PGlite и не запускает доставку Discord. Рабочий хост использует постоянный PostgreSQL и два процесса.

## 4. Загрузка страниц и общие модули

`api-client.js` предоставляет совместимые `from`, `rpc`, `auth` и `storage`. Все операции проходят через API; имя `supabase` в совместимом интерфейсе не означает подключение к облаку.

`config.js` задаёт текущий домен и проверку безопасных URL. `auth.js` получает сессию, `roles-engine.js` загружает права и управляет видимостью элементов. Сервер проверяет каждую операцию независимо от кнопок и `data-perm`.

`main.js` управляет меню, темой, поиском и навигацией. Убрана задержка переходов с затемнением. Фоновая анимация включается по желанию; учитывается уменьшение движения. `stability.css` убирает повторяющиеся появления и скачки карточек. Эмблема шапки хранится локально.

## 5. Авторизация и модель доступа

Свободной регистрации нет. Первый администратор создаётся локальным инструментом на пустой БД. Сотрудников создаёт администратор в личном кабинете. Отсутствие администраторов в таблице не открывает самоназначение через сайт.

Пароли хранятся как scrypt-хеши, токены сессий — как хеши. Изменение пароля требует текущий пароль и завершает сессии. Отключение сотрудника также завершает сессии. Собственная и администраторские записи защищены от удаления через интерфейс.

| Роль | Поведение |
|---|---|
| `admin` | Пользователи, роли, вебхуки и администрирование |
| `ss` | Старший состав; действия определяет `custom_roles.permissions` |
| `user` | Ограниченный доступ; нет изменения чужих заявок, баллов и состава |
| Пользовательская | Явные разрешения разделов, назначается администратором |

Примеры разрешений: `composition:edit`, `supply:view`, `supply:replace`, `supply:delete`, `tests:stats`, `tests:reset_attempts`. Управление ролями и секретами не делегируется обычным ролям. Пользовательская роль не может стать базовой `admin`. Discord-роли не предоставляют доступ на сайт.

Права применяются к разделу целиком. Автоматической изоляции записей по отделу нет: не выдавайте просмотр дисциплинарного раздела тем, кому нельзя видеть его записи.

## 6. Настройка и работа через сайт

### Личный кабинет и роли

`lk.html` — учётные записи, назначение ролей, настройки и лента событий. `roles.html` — роли и разрешения. Окончательное решение о доступе принимает `server/policy.mjs`.

### Формы и обращения

`requests-settings.html` управляет параметрами и полями. Увольнительные, отпуска IC/OOC, увольнение, повышение и восстановление используют `requests` / `request_forms`. Рассмотрение — `requests-review.html`, статистика — `requests-stats.html`.

Прямая страница `service-requests.html` предоставляет формы приёма, заявки в подразделение, перевода, допуска, военного билета, обучения, инструктора, обжалования, аудита склада и предложений. Обязательность и допустимые значения проверяет сервер. Назначение уведомления задаётся в интеграциях.

Электронные заявления принимаются формами сайта и рассматриваются в `requests-review.html`. Импорт сообщений внешнего бота удалён. Жалобы используют `complaints.html`, конструктор `complaints-form.html`, рассмотрение `complaints-review.html`, настройки и статистику. История решений и дисциплинарный реестр хранятся отдельно от формы.

### Состав — `composition.html`

Перенесён редактор ЦГБ с армейской структурой: настраиваемые категории и старшинство; должности командования; подразделения, названия, сокращения, цвета и эмблемы; колонки и раскладка строк; ФИО, статик, спецсвязь, Discord ID; фото с масштабом и положением кадра; PNG всей иерархии или отдела с выбором масштаба, фото и контактов.

Состояние хранится в `composition`, `id=1`, поле `state`. Персональные записи не зашиты в исходники. Для включения сотрудника в ВП и премирование заполните ФИО и статик `000-000`.

### Проверки ВП

`vp.html` получает сотрудников из состава сайта, позволяет отмечать документы и доказательства, сохранять архив проверки. Обновление списка не требует бота. Группировка — по подразделениям сайта, не по Discord-ролям. Используются `vp_checks`, `vp_archive`, `vp_role_mapping`, `vp_report_requests`. Отчёт отправляется через вебхук `vp`.

### Премирование

`payroll.html` получает подразделения и сотрудников из того же состава, создаёт черновик фонда, сохраняет доли, исключения и ручные суммы. Перед отправкой доступны проверка расчёта и экспорт. Worker передаёт данные приказа текстовым приложением. Автоматической архивации после отправки нет; черновик остаётся на сайте.

### Экзамены

`tests.html` — каталог, категории, статистика; `test-editor.html` — редактор; `test.html?t=UUID` — прохождение. Поддерживаются одиночный/множественный выбор, порядок, служебные поля и изображения.

Редактор задаёт публикацию, порог, лимит попыток, таймер, случайную выборку и перемешивание. Сервер фиксирует снимок вопросов и вычисляет результат. Записать балл обычным запросом таблицы нельзя. До начала попытки клиент получает метаданные; ключи ответов доступны редактору, а не посетителю.

Лимит действует по аккаунту, также учитывает статик и Discord. Замена ника не обнуляет лимит аккаунта. Сброс требует отдельного права и причины, сохраняет аудит и учитывает незавершённые попытки.

### Лекции и материалы

`learn.html` — материалы по категориям. `training.html` — лекции, редактор, прочтение, ссылки на тесты. Обе страницы читаются по прямому URL и скрыты в меню. В поставке — вводные памятки и два учебных примера тестов; официальные нормы и полноценный банк публикует командование.

### Контент и документы

`news.html` — новости; `info.html` — информация; `ustav.html` — главы устава; `faq.html` — вопросы; `autopark.html` — техника и фото; `map.html` — карта; `docs.html` — подготовка документов. Контакты лидера для передачи находятся в README.

### Новый учёт поставок

`supply.html` — запрос; `supply-admin.html` — форма запроса. `supply-report.html` и `supply-stats.html` — новый журнал фактических поставок:

- направления **РЛС, ВС, ОБ-7**, получатель, дата/время, доставка и сопровождение;
- выехавшие/прибывшие машины и десять организаций с отдельными цветами;
- серверный итог участников и проверка количества машин;
- фильтры по московским датам, сводка и постраничная история;
- черновик на устройстве, повтор последней поставки, обнуление и возврат состава;
- защита от повторного создания и изменения устаревшей версии;
- мягкое удаление, восстановление администратором и история версий;
- CSV/JSON всех записей выбранного периода, PNG сводки;
- отправка и последующее обновление того же сообщения Discord.

Используются `supply_ledger` и `supply_ledger_history`. Старые `supply_requests` содержат входящие запросы, а не статистику нового журнала. Облачные данные Firebase автоматически не импортируются и не читаются этой версией.

### Служебные отчёты

`report.html` строит форму из `report_forms`; `report-settings.html` настраивает поля и типы. Запросы `report_send_requests` передаются worker через вебхук `reports`.

## 7. Уведомления и журнал событий

Всплывающие уведомления доступны после входа. Предпочтения звука и оформления сохраняются на устройстве. Серверный `audit_log` фиксирует входы, административные действия, изменения таблиц и специальные операции. `GET /api/v1/audit` доступен администратору.

Лента событий личного кабинета и серверный аудит — разные источники: первая собирает события модулей, второй используется для технической проверки. Поставки дополнительно имеют снимки версий в `supply_ledger_history`.

## 8. Discord-вебхуки вместо бота

**[Отдельная инструкция: какие вебхуки создать, каналы и назначение](docs/WEBHOOKS.md).** Администратор вводит URL в `integrations.html` и включает маршрут. Доступны `supply_requests`, `supplies`, `requests`, `complaints`, `exams`, `reports`, `payroll`, `vp`, `warehouse`. Несколько маршрутов можно направить в один текстовый канал.

URL шифруется AES-256-GCM; API показывает только признак настройки. Worker запрещает перенаправления и массовые упоминания, учитывает 429, сохраняет ошибку и ID сообщения. Неопределённый результат первой отправки не повторяется автоматически во избежание дублей.

Вебхуки не читают участников/роли и не принимают вердикты кнопками Discord. Решения принимаются на сайте. Чтение Discord-ролей отложено по согласованию; источник сотрудников — состав сайта. Исторические ID каналов не управляют доставкой.

## 9. Telegram

Telegram-бот не требуется и не запускается. Контакты Telegram служат для связи с ответственными. Исторические `tg_*` структуры сохранены в базовой схеме для совместимости, но публичный API не предоставляет произвольный доступ к ним. Telegram-токены не нужны.

## 12. Фоновые обновления

Облачного Realtime нет. Сохранённые подписки опрашивают разрешённые данные и вызывают обработчик только при изменении снимка. Опрос пропускается в скрытой вкладке.

Журнал поставок обновляется после действий или кнопкой «Обновить» и не перезаписывает открытую форму фоновым рендером. Устаревшее сохранение получает конфликт версии и не затирает чужую правку.

## 13. Изображения и экспорт

Фото сохраняются в `MEDIA_ROOT`. Проверяются право редактирования, сигнатура PNG/JPEG/WebP и лимит 8 МиБ. Чтение собственных медиа требует сессию. Каталог не входит в Git и резервируется вместе с БД.

Состав экспортируется локальным `html2canvas`. PNG поставок строится локально; CSV защищает текстовые ячейки от формул. Экспорт проходит все страницы результата и не ограничивается первыми 100 или 2 000 строками. Внешние материалы и шрифты зависят от своих источников; эмблема и стили находятся в проекте.

## 14. API автономной версии

Все маршруты под `/api/v1`.

| Маршрут | Назначение |
|---|---|
| `GET /health` | Связь с БД |
| `/auth/session`, `/auth/login`, `/auth/logout` | Сессия |
| `PATCH /auth/user` | Изменение пароля с текущим паролем |
| `/auth/admin/users` | Сотрудники, только администратор |
| `POST /db/query`, `/db/rpc/:name` | Разрешённые таблицы и операции |
| `GET /directory` | Состав для ВП / премирования |
| `GET`, `POST /supply-ledger` | Фильтры, сводка, создание поставки |
| `POST /supply-ledger/:id/:action` | `update`, `delete`, `restore`, `send` с версией |
| `GET /supply-ledger/:id/history` | История поставки |
| `/storage/:bucket/...` | Загрузка и удаление фото |
| `/integrations`, `/integrations/:id` | Вебхуки и состояние очереди |
| `GET /audit` | Серверный аудит |

Сервер проверяет Origin изменяющих запросов, частоту, размер тела, имена таблиц/колонок; значения передаются параметрами SQL. Секреты и внутренние таблицы не выдаются произвольными запросами.

## 15. Окружение и запуск

Требуются Node.js 24 и PostgreSQL 17 для постоянного хостинга. Шаблон — [`.env.example`](.env.example).

| Переменная | Назначение |
|---|---|
| `NODE_ENV` | `production` на хосте |
| `HOST`, `PORT` | Loopback-адрес и порт API |
| `PUBLIC_ORIGIN` | Точный HTTPS origin без завершающего `/` |
| `DATABASE_URL` | Ограниченная роль приложения |
| `MIGRATION_DATABASE_URL` | Владелец для миграций |
| `PGSSL` | `disable` для локальной БД либо `verify-full` |
| `WEBHOOK_ENCRYPTION_KEY` | 32 случайных байта, 64 hex-символа |
| `MEDIA_ROOT` | Постоянный каталог фото |
| `TRUST_PROXY` | `1` только за единственным доверенным прокси |

Локальная проверка:

```sh
npm ci
npm run build:frontend
npm run check
npm test
npm run preview
```

Адрес: `http://localhost:18933`. Случайный логин/пароль записывается в `.local/preview-login.json`, БД пересоздаётся при каждом старте. Это не постоянный хостинг.

На хосте: `npm ci --omit=dev`, настройка окружения, `npm run db:migrate`, применение `database/runtime-grants.sql`, первый администратор через `npm run user:create`, запуск API/worker по [инструкции](docs/DEPLOYMENT.md). Пароли не передаются аргументами команд и не коммитятся.

## 17. Связь разделов и передача

Состав → подразделения/сотрудники → ВП и премирование. Лекция → экзамен → серверная попытка → результат. Форма → проверка → заявка → рассмотрение → уведомление. Фактическая поставка → история и сводка → очередь → обновляемое сообщение Discord.

Запрос поставки не подтверждает её фактическое выполнение. Добавление карточки в состав не выдаёт аккаунт или права.

Перед производственным запуском техадмины проверяют свой PostgreSQL, HTTPS, восстановление бэкапа и реальную доставку каждого включённого вебхука. Локальные проверки не заменяют проверку инфраструктуры. Выполненные сценарии и ограничения — в [отчёте передачи](docs/HANDOFF.md).
