# Развёртывание

Требуются Node.js 24, npm, PostgreSQL 17, HTTPS-прокси, два постоянных процесса (API и worker). PostgreSQL не публикуется в интернет. Supabase/PostgREST и Discord-бот не нужны.

1. Разместить проект в `/opt/army`, выполнить `npm ci --omit=dev`. Создать отдельного системного пользователя `army`, каталог `/var/lib/army/media` с доступом на запись для него.
2. Создать БД `army`, роль-владельца `army_owner` для миграций и ограниченный LOGIN `army_runtime` для приложения. Задать уникальные пароли через защищённую консоль PostgreSQL. Обе роли — NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS.
3. Скопировать `.env.example` в `.env`, заполнить адрес БД, точный PUBLIC_ORIGIN без завершающего `/`, ключ шифрования и каталог медиа. Ключ: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Хранить `.env` с правами 600; сохранить резервную копию ключа отдельно от БД.
4. Выполнить `npm run db:migrate`. Инструмент использует MIGRATION_DATABASE_URL, контрольные суммы и advisory lock. Применённые миграции не менять.
5. От имени владельца выполнить `database/runtime-grants.sql`; имя runtime-роли в примере — `army_runtime`. У приложения нет DDL и прав управления PostgreSQL-ролями. Не выдавать runtime владение таблицами или членство в owner.
6. На пустой БД создать первого администратора командой `npm run user:create`, передав JSON через stdin: поля `email`, `display_name`, `password` (не менее 12 символов). Пароль не помещать в аргументы команд или Git. Инструмент откажет, если пользователи уже существуют. При восстановлении администратора на действующей БД требуется отдельное локальное обслуживание владельцем БД; веб-интерфейс не имеет обходного bootstrap.
7. Установить службы по образцам `deploy/army-api.service` и `deploy/army-worker.service`. API слушает loopback:8787. `npm start` и `npm run worker` можно запустить вручную для диагностики. Worker нужен для Discord, API работает без него.
8. Настроить HTTPS-прокси по `deploy/nginx.conf`, сертификат своим штатным способом. TRUST_PROXY=1 допустим только при одном доверенном прокси и недоступном извне порте API. Прокси передаёт исходный Host/Origin, не заменяет Origin.
9. Войти, проверить сохранение новости, создание сотрудника, роли, тест, заявку, поставку и вебхук. В `integrations.html` ввести URL нужных вебхуков и включить маршруты.

## Проверка и эксплуатация

`GET /api/v1/health` проверяет подключение к БД. Следить за журналами обеих служб и очередью уведомлений. Не включать логирование тела запросов: в нём могут быть пароли и вебхуки. Логи сервера не выводят SQL и секреты.

Бэкап: `pg_dump -Fc` БД, каталог медиа и ключ WEBHOOK_ENCRYPTION_KEY. Регулярно проверять восстановление в отдельную БД. При обновлении: бэкап → остановка worker/API → миграции owner → обновление grants при появлении таблиц → запуск → проверка health и входа. Откат схемы — восстановление проверенного бэкапа, а не автоматический down.

При переносе из Supabase не выполнять исторический SUPABASE-SETUP.sql. Текущие миграции предназначены для новой БД. Перенос существующих данных требует сопоставления UUID, схемы и пользователей; пароли Supabase не импортируются автоматически. Исторические записи с персональными данными не включены в репозиторий.
