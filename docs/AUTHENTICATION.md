# Авторизация по статику и регистрация сотрудников

**Единственный способ входа — статик `000-000` и пароль. Вход по почте удалён из интерфейса и API, в том числе для администраторов.**

- `account.html` — отдельная страница входа и проверки состояния ранее поданной заявки.
- `register.html` — отдельная страница регистрации.
- `accounts-review.html` — рассмотрение заявок сотрудниками с правом `registration.review`.

Приём новых заявок по-прежнему **выключен по умолчанию**: `REGISTRATION_ENABLED=false`. Этот флаг управляет регистрацией и рассмотрением заявок. Вход уже созданных аккаунтов по статику работает независимо от него, чтобы администратор мог подготовить доступ. Внешних провайдеров, Firebase, почтовой рассылки или Discord-бота нет.

## Заявка

Обязательны имя и фамилия персонажа, статик, должность, звание, Discord (имя пользователя или числовой ID), пароль с повтором и **фото игрового УДО**.

Статик — ровно шесть ASCII-цифр и обычное тире: `000-000`, всего семь знаков. Пробелы, перенос строки, буквы, другое тире и запись без тире отклоняются сервером. Пароль — 12–128 символов, хранится как scrypt-хеш. Должность и звание не дают прав: роль сайта назначает проверяющий отдельно.

Заявка остаётся в `pending` до решения. Вход с её статиком и паролем показывает только её состояние и причину отказа, если она есть. До одобрения портальная сессия не создаётся. При одобрении создаётся аккаунт с выбранной ролью, прежним паролем и проверенными полями анкеты. Правильность статика, должности, звания и Discord проверяет сотрудник по игровым данным и УДО; автоматической проверки Discord нет.

## Фото УДО и приватность

Форма принимает JPEG, PNG, WebP до 10 МБ. Браузер уменьшает изображение до 1600 пикселей по большей стороне и готовит JPEG до 1 МБ. Сервер независимо ограничивает размер, действительно декодирует изображение через `sharp` с лимитом входных пикселей, отклоняет SVG/повреждённые и многокадровые файлы, заново кодирует JPEG и удаляет исходные метаданные. Итог хранится в приватной таблице `registration_identity_documents` (bytea), а не в `public` или `/media`.

Фото выдаётся только через защищённый маршрут `GET /api/v1/accounts/review/:id/udo` сотруднику с актуальным правом рассмотрения, включая администратора. Ответы — `Cache-Control: no-store`, `image/jpeg`, `nosniff`. Список заявок содержит только признак наличия фото; изображение загружается при раскрытии карточки. Общий API таблиц не выдаёт ни документы, ни хеши паролей. Фото и анкета не отправляются вебхуком, не попадают в Git или серверный аудит. Бэкап БД содержит фотографии и требует такого же ограничения доступа, как сама БД.

## Подключение на новой установке

1. Установить зависимости через `npm ci --omit=dev` (включая `sharp`), настроить PostgreSQL, HTTPS и точный `PUBLIC_ORIGIN` по [DEPLOYMENT.md](DEPLOYMENT.md).
2. Применить миграции `001`–`009` командой `npm run db:migrate`, затем повторить [runtime-grants.sql](../database/runtime-grants.sql) от владельца БД. Не давать runtime-логину права владельца или DDL.
3. На пустой БД создать первого администратора: `npm run user:create`. Передать JSON через stdin с `static_id`, `display_name`, `password`. Настоящий статик администратора назначает техадминистратор; контакты лидера из README автоматически прав не дают. Пароль не передавать аргументом командной строки или сохранять в Git.
4. Войти на `account.html` по этому статику и паролю. Почта не используется.
5. На странице «Роли и права» включить **«Рассматривать регистрации и назначать доступные роли»** у выбранных служебных ролей. Не включать право у общего «Сотрудника», если рассматривать должны только ответственные. Назначить роли проверяющим в личном кабинете. Администратор имеет право рассмотрения по умолчанию.
6. Подготовить роли новых сотрудников. Проверяющий может выдавать лишь разрешения, которые есть у него самого; роли `admin`, управление доступом и делегирование рассмотрения через обычного проверяющего запрещены.
7. Когда всё готово, установить в приватном `.env` `REGISTRATION_ENABLED=true`, перезапустить API. Worker и вебхуки для авторизации не нужны.
8. Проверить обязательные поля, файл УДО, ожидание без доступа, одобрение с выбором роли, отказ с причиной и вход после одобрения. Проверить, что обычный сотрудник и аноним не открывают фото чужого УДО.

## Обновление существующей установки

**До замены API подготовить подтверждённые статики для существующих аккаунтов, включая администратора.** Миграция 009 отзывает старые сессии. Аккаунт без `users.static_id` после обновления войти не сможет; почтового обхода нет.

После резервной копии, остановки API/worker, применения миграций и grants техадминистратор выполняет `npm run user:bind-static`, передавая через stdin JSON с `user_id` (UUID существующего аккаунта) и `static_id` (подтверждённый статик). Инструмент работает локально с БД, не меняет пароль/роль, отказывается заменять другой существующий статик или присваивать статик чужой заявки, отзывает сессии и пишет событие в аудит. UUID можно посмотреть локально запросом `SELECT id, email, static_id FROM users`. Старое поле email остаётся только для совместимости схемы, оно не является способом входа.

Не создавать дубликат аккаунта для перехода с почты. Старые заявки без новых полей и УДО невозможно одобрить: ответственный должен отклонить неполную заявку; после проверки личности техадминистратор архивирует её в защищённом бэкапе и удаляет локально для повторной подачи либо дополняет её проверенными данными через обслуживание БД. Не публиковать заявку или фото для такого переноса.

Применённые миграции не изменять. Изменения текущего обновления: [009-registration-identity.sql](../database/009-registration-identity.sql). Порядок — бэкап → остановка процессов → миграции → grants → привязка статиков → запуск → проверка входа → включение регистрации по готовности.

## Права и обслуживание

- Для одобрения обязательна конкретная существующая роль и полная анкета с УДО.
- Системный `admin` и административные базы через регистрацию не выдаются даже администратором.
- Проверяющий не может назначить роль выше своих разрешений, старший состав при собственной базе `user`, или роли с правами `lk`, `integrations`, `registration`. Только администратор выдаёт право рассмотрения.
- Решение выполняется транзакцией с повторной проверкой актуальных прав и блокировкой заявки. Одновременное рассмотрение не создаёт второй аккаунт. Решение и изменения прав пишутся в `audit_log`, без фото и паролей.
- Изменение роли и отключение действующих аккаунтов выполняет администратор в личном кабинете. Создание аккаунта администратором также требует статик, а не почту.
- Забытый пароль восстанавливает техадминистратор после проверки личности: формирует новый scrypt-хеш через `passwordHash` из `server/security.mjs`, обновляет соответствующую запись в `users` или `registration_requests`. Для действующего аккаунта обязательно удаляет его `auth_sessions`. Публичного сброса по почте нет.
- Внутренний адрес `000-000@accounts.vsrf.invalid` нужен только старым модулям и уникальному полю схемы. Это не почтовый ящик и не действующий логин.

Сессии: HttpOnly, SameSite=Strict, Secure в production, срок 8 часов. Все изменяющие запросы требуют правильный Origin. Лимит входа общий для `/auth/login` и `/accounts/login`: 15 запросов/15 минут/IP. Регистрация: 5 запросов/час/IP. Не логировать тела запросов. При нескольких экземплярах API настроить общий лимит на прокси: встроенные счётчики находятся в памяти процесса.

Отключение `REGISTRATION_ENABLED` останавливает приём/рассмотрение заявок, но не блокирует статик-вход существующих пользователей и не отзывает их сессии. Для блокировки пользователя отключить его аккаунт. Публичные страницы остаются публичными.

## Маршруты и данные

| Маршрут `/api/v1` | Назначение |
|---|---|
| `GET /accounts/config` | Публичный флаг приёма регистраций |
| `POST /accounts/register` | Подача полной анкеты и УДО |
| `POST /accounts/login`, `POST /auth/login` | Один обработчик статика и пароля; email отклоняется |
| `GET /accounts/review?status=pending` | Очередь; также `approved`, `rejected` |
| `GET /accounts/review/:id/udo` | Защищённое фото для проверяющего |
| `POST /accounts/review/:id` | Решение и назначение роли |
| `POST /accounts/reviewer-roles/:id` | Только администратор, настройка права рассмотрения |

Миграция 008 создаёт заявки и уникальный статик пользователя. Миграция 009 добавляет `position`, `military_rank`, `discord` и таблицу `registration_identity_documents`. Фото хранится в этой таблице с внешним ключом на заявку; удаление заявки удаляет и её фото. Новые поля nullable исключительно для совместимости старых записей: сервер требует их при подаче и при одобрении. После одобрения хеш пароля переносится в `users`, анкета попадает в `user_metadata`, фото остаётся приватным приложением к заявке. Сроки хранения задают техадминистраторы по принятой процедуре; автоматического удаления фото в этой версии нет.
