# Права и безопасность

Проверка выполняется на сервере для каждого запроса, независимо от скрытых кнопок и `data-perm`. Сессии — случайный токен в HttpOnly/SameSite=Strict cookie; в БД хранится хеш. Production требует HTTPS и Secure cookie. Пароли — scrypt, минимум 12 символов. Публичной регистрации нет.

## Четыре исходных критических риска

1. Политики `write_auth ... using(true)` не используются. Браузер обращается к собственному API; таблица и действие проверяются по серверной карте прав. Нет общедоступного PostgREST.
2. Пустая таблица администраторов не разрешает самоназначение. `staff_upsert_role` требует действующего администратора и разрешает только user/ss. Создать admin через HTTP нельзя. Системную роль admin и собственную роль нельзя изменить через этот RPC.
3. Аноним не читает состав, заявки, жалобы, сотрудников Discord, премии, наказания, ответы и попытки. Публичны информационные страницы, учебные материалы, описания опубликованных тестов и шаблоны форм. В исходном JS состава удалены старые ФИО/статики; структура должностей сохранена.
4. Ключи ответов доступны только редактору экзаменов. Начало и завершение теста требуют входа. Лимиты привязаны к user_id и дополнительно к статику/Discord; изменение введённых данных не даёт новую попытку тому же аккаунту. Баллы и срок проверяет сервер, старая небезопасная submit_test_attempt недоступна. Повторная отправка завершённой попытки возвращает тот же результат.

## Роли

`admin` создаётся локально, управляет пользователями, пользовательскими ролями и вебхуками. `ss` получает права из системной роли старшего состава. `user` имеет базовое чтение учебных разделов и внутреннего состава. Дополнительная custom-role задаёт действия по разделам: view/edit/delete, review, settings, submit/send, stats/reset_attempts, replace/admin для поставок. Источник истины — `server/policy.mjs`. Управление доступом и секретами не делегируется пользовательской роли.

Не назначать ss всем подряд: это широкая служебная роль. Для узкой обязанности создать custom-role с минимальным набором разрешений. Роль применяется сервером при каждом запросе; изменение роли отзывает сессии пользователя.

Запросы параметризованы, идентификаторы проверяются. Изменяющие API-запросы принимаются только с точным Origin; CORS не включён. Есть ограничения частоты, размера JSON и загрузок. Для исходных inline-скриптов CSP использует хеши; произвольные inline-скрипты запрещены. Медиа допускают PNG/JPEG/WebP, защищены входом. Приватные каталоги не раздаются.

Проверки автоматизированы в `tests/core.test.mjs`. Это проверка реализованных сценариев, а не гарантия отсутствия всех уязвимостей. Отдельная изоляция по подразделениям в старой модели данных не заявляется: чтение раздела даёт доступ к его записям. Прямой доступ к БД допустим только техадминам и API; runtime PostgreSQL-логин сам по себе является доверенным серверным секретом.
